# BGTS-OS Database — Schema Reference (v2)

This document covers what's been built so far: a complete, verified Postgres schema
for BGTS-OS, designed against the app's *actual* current data model (not a generic
template) and validated against a real Postgres engine before being handed to you.

**Status:** schema + login screen are built. The `store.js` data-access layer that
actually reads/writes Supabase (instead of AsyncStorage) has not been built yet —
see "What's next" at the end.

## ⚠️ Correction — action required if you already ran the v1 migration

The first version of `0001_schema.sql` typed every `id` (and every foreign key)
column as `uuid`, generated by the database (`default gen_random_uuid()`). That
was wrong: this app generates its own ids client-side, in every screen, via
`uid()` in `src/logic.js` — plain strings like `lr1a2b3c4d`, not UUIDs. A `uuid`
column physically cannot store that value, so every insert coming from the real
app would have failed once wiring began.

**Every id/foreign-key column is now `text`** (the app supplies the value), except
`app_users.id` and `status_history.changed_by`, which stay `uuid` because those are
real Supabase Auth user ids, not app-generated ones. Corrected and re-verified
end-to-end against a real Postgres engine (36 tables, RLS, triggers, constraints,
and a new upsert-does-not-duplicate check, all passing).

**If you already ran the old `0001_schema.sql` in your Supabase SQL Editor**, that
schema has the wrong column types and needs to be reset — it's empty (no real data
has been synced into it yet), so this is safe and only touches `bgts_os`:

1. In the Supabase SQL Editor, run: `drop schema bgts_os cascade;`
2. Re-run the three files in `supabase/migrations/` in order: `0001_schema.sql` →
   `0002_functions.sql` → `0003_rls.sql`.
3. Nothing outside `bgts_os` is touched — your website's `public` schema tables
   (`bookings`, `mvd_bookings`, `website_inquiries`, `trip_expenses`, etc.) are
   completely unaffected by this or any step above.

If you haven't run any migration yet, just use the current files — no extra step
needed.

## 1. Why a separate schema, not a separate project

You mentioned reusing the Supabase project you already have for the BGTS website.
Every table below lives inside its own Postgres schema, `bgts_os`, instead of the
default `public` schema. That means:

- Nothing here can collide with whatever tables the website already has.
- You can `DROP SCHEMA bgts_os CASCADE` at any point during testing without touching
  anything else in that project.
- One Supabase project, two cleanly separated schemas.

## 2. Files

```
supabase/migrations/
  0001_schema.sql      Tables, columns, constraints, indexes
  0002_functions.sql   Atomic counters, updated_at triggers, auth-user provisioning, 2 views
  0003_rls.sql         Row Level Security — enabled on every table
```

Run them **in this order**, once each, in your Supabase project's SQL Editor
(Dashboard → SQL Editor → paste → Run). They're written to be safely re-runnable if
you need to re-apply one (uses `if not exists` / `drop ... if exists` / `on conflict`
throughout).

**Verification already done:** all three files were executed end-to-end against a
real embedded Postgres engine before delivery — not just read for syntax. Confirmed
working: all 36 tables + 2 views create cleanly; every id/FK column is `text` except
`app_users.id` (correctly still `uuid`); RLS is ON for every real table;
`next_counter()` increments atomically; foreign keys enforce correctly with
plain-string app ids; duplicate LR numbers, duplicate LR party roles, and invalid
status values are correctly rejected by constraints; re-inserting the same LR id
with `on conflict (id) do update` updates the one row rather than creating a second
one; a new `auth.users` row automatically provisions an `app_users` profile row via
trigger.

## 4. Key design decisions (and why)

- **`lr_goods` is a child table, not a comma-separated field.** One LR can have many
  goods rows; each is its own row with a `sort_order`, exactly as requirement #10 asked.
- **`lr_parties` normalizes consignor/consignee/billing-to** into one table with a
  `role` column and a `unique(lr_id, role)` constraint, instead of 15 duplicated
  columns (5 fields × 3 party types) on the `lrs` table.
- **`lr_charges` is 1:1 with `lrs`**, one column per charge type (freight, surcharge,
  loading, GC charge, etc.) — nothing is pre-summed into a single opaque total; GST
  math still happens the same way, just reading from real columns instead of a JS object.
- **`invoice_bookings` is a junction table**, not an array column — the app's
  `invoice.bookingIds[]` becomes a proper many-to-many relationship.
- **`counters` + `next_counter()`** replace the app's client-side `db.seq` object.
  The old approach (read a number, increment in JS, write it back) has a real race
  condition once more than one person can write to the same database at once — two
  people creating an LR at the same moment could get the same number. The new
  function does the read-increment-write as one atomic database statement.
- **`acct_expenses.id` reuses the app's existing dedup pattern directly**
  (`'hadv_' + lrId`, `'hpay_' + paymentId`, generated in `LRFormScreen.js` /
  `LRScreen.js` today) instead of a database-generated key. Because that id *is*
  the primary key, re-saving an LR or hire payment upserts its own postings in
  place instead of creating duplicates — this directly matches your "no
  duplicates" requirement (#21), and required no new logic since the app already
  computes these deterministic ids.
- **`lhcs.lr_nos` stays free text.** In the current app this is genuinely just a text
  field, not a real link to `lrs` — preserved as-is rather than inventing a
  relationship the app doesn't actually have.
- **Two read-only views** (`lr_hire_summary`, `invoice_balances`) precompute the same
  balance/outstanding math the app's `lrHireBalance()`/`invOutstanding()` functions do
  today, so the frontend can read one row instead of re-deriving it from three tables
  every time.

## 5. Security model (RLS)

The app had no login before this rollout. A basic Supabase email/password login
screen has now been added (`src/LoginScreen.js` / `src/AuthProvider.js`, wired in
`App.js`) — the minimum needed for RLS to mean anything, and the one UI addition
you explicitly approved.

The policy is: **every table requires authentication.** The `authenticated` role
(anyone logged in) can read and write
everything — one shared company account, matching how the app already behaves (one
shared data blob, no per-record ownership). The `anon` role (not logged in) gets
nothing at all: no table is readable or writable pre-login.

`app_users` has a slightly different policy: any logged-in user can see the full
list (so audit history can show "changed by so-and-so"), but can only edit their own
row.

If you later want real per-role permissions (e.g. a driver-only login that can only
see their own trips), that's a policy change on top of this schema, not a rewrite —
`app_users.role` already exists as the hook for it.

## 6. Environment variables (read by `src/supabaseClient.js`)

```
EXPO_PUBLIC_SUPABASE_URL=<your project URL>
EXPO_PUBLIC_SUPABASE_ANON_KEY=<your anon/public key>
```

The `EXPO_PUBLIC_` prefix is Expo's required convention for any variable that needs
to be readable in the browser bundle (this is a static web export, so there's no
server to hide it behind) — this is the anon key, which is safe to expose by design;
Row Level Security is what actually protects the data, not keeping this key secret.

**The service-role key is never used anywhere in this plan.** Migrations are run by
you, by hand, in the Supabase SQL Editor — I never need or ask for that key.
